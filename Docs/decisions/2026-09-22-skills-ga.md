# Move `SkillsService` onto the GA Skills API

**Date:** 2026-09-22
**Roadmap entry:** "Move `SkillsService` onto the GA Skills API" (top of `ROADMAP.md`)

## Goal

Make `client.skills` work against the Skills API that Anthropic actually serves, without breaking
any call site that compiles against the current release.

## What we believed, and what we found

`ROADMAP.md` framed this as a risk: the service sends `anthropic-beta: skills-2025-10-02`, the GA
object has no `name`, and *"if the header stops being honoured, decoding throws instead of
degrading."* That is wrong in the direction that matters.

Retrieved 2026-09-22:

- <https://platform.claude.com/docs/en/api/skills/list> — GA
- <https://platform.claude.com/docs/en/api/beta/skills/list> — the `skills-2025-10-02` variant

`skills-2025-10-02` is **still a live beta value** — it appears in the `anthropic-beta` enum on the
beta reference page, alongside 46 others. So the header has not been retired. But the beta document
and the GA document describe **the same object and the same envelope**: `display_name`,
`latest_version_id`, `source`, `updated_at`, and a `next_page` token. Neither returns `name`.
Neither returns `has_more`, `first_id` or `last_id`.

So this was never a future risk. `Skill` required `name: String` and `Page` required
`has_more: Bool`, and the API returns neither under either header. **Every `client.skills` call
throws `AnthropicError.decodingError` today, and did on the day it shipped.** The header is not what
protects it; nothing does.

The suite was green throughout because the fixtures in `SkillsServiceTests` were written to match
the shape the SDK invented. A test that decodes with the same assumption that encoded proves
self-consistency, not correctness. The new `SkillDecodingTests` copy the vendor's literal
`Response (200)` bodies and cite the page each came from.

`create` is wrong in a second way the roadmap did not record: the GA endpoint is
`multipart/form-data` taking a `files` array, not a JSON body of `{name, description, parameters}`.

## Approach chosen

Additive except in two places, both named in `CHANGELOG.md` rather than papered over: `delete(id:)`
returns `SkillDeleteResponse` instead of `Void` (`@discardableResult`, so only an unapplied
function reference or a `return` in a `Void` function breaks), and `list(limit:afterId:)` lost the
default on `afterId` — which is exactly what keeps a bare `list()` unambiguous against the new
overload. Everything else grows:

- `Skill` gains `displayName`, `latestVersionId`, `source`, `updatedAt`. `name` becomes a deprecated
  computed alias for `displayName`, so `skill.name` still compiles and now returns the right string.
  `Skill` has no public initializer (its memberwise init is internal), so replacing a stored
  property with a computed one cannot break a caller.
- Every field added after the SDK's first Skills release decodes with `decodeIfPresent`. A response
  missing one degrades instead of throwing.
- `displayName` falls back to a `name` key when `display_name` is absent, so a deployment pinned to
  the pre-GA shape still decodes. The pre-existing `SkillsServiceTests` pass unmodified because of
  this, which is the backward-compatibility claim demonstrated rather than asserted.
- `SkillSource.type` is a `Kind` enum, `RawRepresentable` with `unknown(String)` carrying the value
  the API sent. A fifth source added later must not make the whole response undecodable — the same
  failure `claude-agent-sdk-go` shipped with invented content-block types. The payload matters for
  a second reason: it makes the mapping total, so `list(source:)` still sends a filter for a source
  this SDK predates instead of dropping it and silently returning everything.
- `Page` gains `nextPageToken: String?` and derives `hasMore` from it when `has_more` is absent. The
  new `init` parameter has a default, so existing initializer call sites are unaffected. Both cursor
  styles decode, because Messages, Models and Files still use the id cursor.

## What the review found that the implementation had wrong

Worth recording, because three of these are the failure mode this whole entry is about — a check
that passes without checking anything.

- **The first end-to-end tests were talking to `api.anthropic.com`.** Four came back `401`; the
  fifth *asserted* a 401 and passed. The cause was `ClientOptions.baseURL(_:)` never reaching the
  HTTP client, which became the second commit on this branch.
- **The three-page pagination test did not exist; the two-page one could not fail.** Page 2 always
  arrived with `next_page: null`, so the fetcher it carried was constructed and never invoked —
  deleting the recursive re-attachment passed the whole suite. Falsified now: removing it fails six
  tests.
- **`testCreateRejectsAnEmptyFileSet` could not fail.** With no handler set, `MockHTTPClient`
  returns `{}`, which fails to decode as a `Skill`, which throws `AnthropicError` — the same type
  the guard throws. Deleting the guard kept it green.
- **CRLF is one `Character` in Swift.** The `Content-Disposition` escaper switched on `Character`
  and let `\r\n` through untouched, which was the entire point of writing it. Caught by the
  end-to-end injection test; now pinned by a unit test asserting `"a\r\nb".count == 3`.
- **`--filter "Integration"` matches no test case.** CI's integration job had been green while
  executing zero tests since it was written.

## Alternatives considered

- **Make `name` an optional stored property.** Rejected: `String` → `String?` is source-breaking for
  every caller that reads it, and the value is available under a different key, so there is nothing
  to be honest about by making it optional.
- **Make `SkillSource.type` a plain `String`.** Rejected: it discards the closed set the docs
  publish and pushes string comparison onto every caller. `RawRepresentable` with an
  `unknown(String)` case gives exhaustive switching without making an unrecognised value fatal, and
  follows `Model`, which the repo already solves this way.
- **A payload-free `unknown` plus a separate `rawType` string.** This is what was written first.
  Rejected on review: it split one value across two properties, needed a second `Kind → String`
  mapping in another file with nothing to keep the two in step, and made that mapping partial —
  `unknown` had no wire value, so `list(source: .unknown)` dropped the filter and returned every
  skill.
- **Add `AnthropicError.invalidRequest` for the `create` validation failures.** Rejected for now:
  adding a case to a public enum breaks exhaustive `switch`es. `encodingError` carries the message,
  and the new `LocalizedError` conformance means `localizedDescription` reports it. Revisit at the
  next major — it is on `ROADMAP.md`.
- **Keep sending the beta header and change nothing else.** Rejected: it decodes identically, so it
  buys nothing and leaves the SDK advertising a beta it does not need.
- **Wait for a live API key before changing anything.** Rejected: the two published documents agree
  with each other and disagree with this SDK. Waiting leaves a service that provably cannot decode
  either shape.

## Libraries added or used

None. `MultipartFormData` (already used by `FilesService`) carries the new `create`.

## Trade-offs and risks

- **No live call was made.** This host has no `ANTHROPIC_API_KEY`, so the contract is verified
  against Anthropic's published response bodies and over a real socket to a loopback server serving
  those bodies — not against `api.anthropic.com`. `LiveSkillsTests` drives the real endpoint and is
  skipped without a key; CI runs it on `main` where the key is available.
- `Skill.description` is `nil` against the current API. It is kept as a decoded optional rather than
  removed, because removing it is a break and it costs nothing to accept one if it appears.
- Skill **versions** are still unmodelled: `latestVersionId` is an id this SDK cannot resolve. That
  is a follow-up roadmap entry, not part of this change.
